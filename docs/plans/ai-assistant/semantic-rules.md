## 规则来源与变更原则

| 状态     | 含义                                                                   |
| -------- | ---------------------------------------------------------------------- |
| 用户明确 | 本次会话直接提出的要求，应作为实现约束                                 |
| 实施默认 | 为推进实现确定的可调整口径；回答应展示相关假设，不能描述成用户亲自确认 |
| 待决定   | 对实现有影响但尚未完成选择；到相应阶段结合源码、数据和评估决定         |

用户明确：自然语言查真实商品、物料和渠道商数据；能理解时间与地点；“配件”应能匹配“配饰”和绿松石圆珠，即使缺少“配件”标签；希望后续支持语音；需要跨 Codex 会话接续开发。

实施默认：首版只读；默认共享业务数据查询；采购采用批次日期；有界范围优先全量检查；事实由后端取值和计算；依据不足不硬猜；对话和结果采用结构化数据。

采购查询的基本关联：`采购明细 → 批次日期 + 渠道商地点 + 目录语义`。先限定授权和明确硬边界，再判断语义；不能只搜目录后把其所有历史批次一并返回。

## 业务规则

### R01：时间解析

- 后端注入当前时间与 `Asia/Shanghai`，模型识别相对时间意图，程序计算并校验边界。
- 固定验收时钟为 `2026-11-16T12:00:00+08:00`。“这个月”对应日期区间 `[2026-11-01, 2026-12-01)`；“上个月”对应 `[2026-10-01, 2026-11-01)`。
- 批次 `receivedAt` 是日期，在现有代码中以 UTC 零点承载；使用日历日期比较，不能把它当北京时间时间戳再偏移一天。
- “买的”实施默认按批次日期，并说明“按采购批次日期查询”。实际付款、到店或出行时间没有字段依据时，不能声称查到了这些事实。
- “今天录入”“这个月建档”用 `createdAt` 和北京时间时间戳范围。相对日期在跨月、跨年时同样由程序计算。

### R02：地点解析

- 区分行政/业务区域、市场、具体店铺。一个市场可以匹配多个渠道商，不必强制让用户只选一家。
- 地址或明确名称匹配可以支持地点归属；区域只能说明较大范围。备注明确提到地点时，要区分“在此经营”和其他语境，不能直接当归属事实。
- 开发库实际区域是“荔湾”，不是“荔湾广场”。9 家荔湾渠道商中 7 家地址包含“荔湾广场”，另 2 家一个有其他地址、一个地址为空。默认只将有明确依据的 7 家纳入精确地点。
- 缺少地点证据的可提示用户补充或列为地点待确认，不能因为“智能”而扩张地点硬条件。
- 当前地址代表当前记录信息。没有历史地址快照时，不声称证明采购当日店铺位置或本人线下到访。

### R03：配件、配饰与形态

- 用户明确：缺少“配件”标签仍需匹配；“配饰”和绿松石圆珠应能纳入。
- 在制作采购语境中，先把“配件”理解为用途概念。圆珠、散珠、桶珠、药片、随形、提溜等制作物料均可提供用途证据；具体归属结合名称、分类和备注判断。
- 上述其他形态的扩展属于实施默认，后续用户可调整。“提溜/吊坠”不能在所有场景全局视为同义：制作物料、成品首饰需要区分。
- 不要求分类名称或标签同时含“配件”。也不能把整个 `Material` 表无条件定义为配件。P3-01 将制作语境的配件/配饰与已定义形态做版本化包含；未覆盖表达不硬猜，且不把圆珠与桶珠、提溜与吊坠作全局同义替换。
- 若仅有成品记录，缺少制作物料依据，不自动纳入“买的配件”；用户明确要“所有绿松石商品和物料”时才扩大对象范围。

### R04：材质与否定证据

- 分类、标签、名称、别名和明确描述可支持“绿松石”材质；艺名、颜色、图片观感、售价不能单独证明材质。
- “绿松石色玻璃珠”“仿绿松石树脂珠”有明确排除依据，不能因子串命中纳入绿松石材质结果。
- 裸词“松石”或模糊艺名不是自动同义词；有实际别名或规则依据时才映射，否则待确认。
- 名称、标签与分类冲突时，保留冲突证据并待确认，不能按固定字段优先级悄悄选一个答案。
- 备注只说“适合搭配绿松石”说明用途，不等于该物料本身为绿松石。“用来搭配绿松石的配件”是另一种意图，应按用户表述处理。

### R05：证据与判定结构

建议的判定状态为 `include`、`exclude`、`uncertain`；`not_evaluated` 是执行状态，不能混入已判断集合。

每个判定至少保留：目录类型与 ID、对应采购行 ID、判定状态、实际字段路径与值、简短理由、适用规则版本。工具必须验证 ID 和字段证据确实来自当前候选。

不使用模型自报的数值置信度替代证据。正式结果纳入 `include`；`uncertain` 单独展示，不能合入确定金额。没有证据的候选不能为了提高召回率直接升级为确定结果。

### R06：查找范围与完整性

- 先按明确时间、地点、权限等限定范围；语义条件在候选查找与判断阶段应用。地点未解决前不宣称范围完整。
- 范围较小时对全部候选分批读取和判断。分类、名称、别名、标签、备注多路查找用于大范围；语义索引仅补充候选。
- 至少区分查询范围是否已解析、候选遍历是否完整、语义判断是否完整，以及是否仍有待确认项。单一 `complete=true` 不足以同时表达这些状态。
- 记录候选总数、已读取数、去重目录数、已判断数、纳入数、待确认数、未评估数。采购行与目录身份的数量应分开。
- 达到预算、模型失败或只取 Top-K 时，明确“尚未检查全部”。0 个已纳入结果不等于无匹配。
- 全部候选判断完成但仍有待确认项时，可以说明“已检查全部候选，另有待确认项”；不能保证语义上的绝对无遗漏。

### R07：数量、金额与汇总

- 目录按 `type + itemId` 去重；采购明细按采购行 ID 去重。同物料不同批次都要保留，不能只取最新一批。
- 物料金额复用现有 `purchaseTotalAmount` 优先、缺失时采用有依据的 `receivedQty × purchaseUnitPrice` 口径；商品采购用 `quantity × unitCost`。缺失不能补零。
- 金额使用 Decimal；展示单位与币种。商品售价 `priceCents` 与采购成本不能混淆；多币种结果分币种统计。当前采购表无独立币种，P2-04 明确标记 CNY 为业务默认，不以目录售价 `Product.currency` 推断历史采购币种；未知币种独立分组。
- 数量按 `STRAND/BEAD/GRAM` 等单位分组，不能把串、颗、克加成“总件数”。展示目录款数、采购行数与采购数量时分别命名。
- 汇总覆盖全部已确定结果，不随 UI 页码变化。已知金额合计与未知金额行数同时返回；有待确认项时不称为完整最终总额。

### R08：库存与追问

- “这些还剩多少”实施默认查询这些目录物料的当前总库存，并明确是当前库存。
- “这次买的还剩多少”查询已选采购批次行的当前剩余量；不能把当前总库存当成该次采购余量。
- 采购量不因库存消耗而变化；未知库存不是零库存。库存读取当前批次 `remainingQty`，复用页面汇总及既有库存更正结果。P2-05 核对当前 DIY 来源仅保存用料/成本，不自动扣减批次库存，不能再次减去 DIY 行用量，尤其不能混减不同 `usageUnit`；详见[库存查询](stock-query.md)。
- 历史采购日期、渠道商和地点仅用于确定对象或来源行；目录当前总库存读取该对象所有当前批次，不套用历史采购筛选。商品只有总库存，没有采购行余量字段，不能推导或替代。
- “只看圆珠”保留已确认日期、地点、材质，增加圆珠形态；不能单凭“桶珠也是珠子”保留桶珠。
- “改成上个月”替换日期；“不限制地点”移除地点。涉及实时事实时重新查询，结果标注查询时间。

### R09：账号、采购人和历史

- 数据访问范围由当前认证与业务权限决定，不能由模型传入的账号 ID 决定。
- 普通“我买的”在当前共享数据语境中采用共享采购数据，并说明口径；如果用户强调“只查我本人采购”，需要可靠采购人字段或澄清。
- `RecordAttribution.createdBy` 是录入者快照，`updatedBy` 是修改者；审计操作不能代替采购行为。历史人员未知不补猜。
- 对话属于账号；不能跨账号读取别人的对话来补齐上下文。是否持久化、保留多久在 P4-03 决定。
- 历史采购对应的目录名称/标签可能已被修改。当前没有相应历史快照时，应说明以当前目录描述解释历史采购。

### R10：无结果、失败和纠正

- 区分查不到、歧义、待确认、工具失败、模型失败、取消与未完成，分别返回明确状态。
- 扩大搜索范围或放宽硬条件要说明变化；不能悄悄删除地点/时间限制来制造结果。
- 用户反馈先关联具体问题、记录、理由和规则版本；只修改当次条件或保存待整理反馈，不直接全局学习。
