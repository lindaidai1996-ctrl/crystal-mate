# 附件双向关联与票据智能归档

批次与渠道商可以共享附件。一张附件可关联多个批次、多个渠道商；关联不会建立采购记录、调整进货归属或改变金额统计。

## 使用

- 在任一详情页的附件区勾选图片，点击“关联渠道商／关联批次”。已有进货关系的目标优先展示，也可搜索其他目标。
- 展开“新上传附件关联到”可预先指定多个目标。详情页上传即保存；新建／编辑抽屉先保存在表单草稿，保存时在同一事务建立附件和关联。
- 图片和备注共享；编辑前展示受影响位置。封面与顺序属于当前位置。更换共享图片时，同步替换使用原图的封面，并使原识别结果失效，不修改物料／商品原图。
- “取消当前关联”只移除当前位置；“彻底删除”在确认全部影响位置后移除所有关联。两者均不删除存储文件。
- 历史记录不按文件自动合并。关联时发现目标已有同一 objectKey 的另一附件，会列出全部影响位置；不同备注必须手动选择。重新上传产生的不同 objectKey 不做视觉去重。
- “智能关联”只处理已经保存、用户主动选择的图片。选择已配置的图片模型后点击识别，核对销售方／购买方、电话和日期，再选择建议或手动搜索，最后集中确认。推荐没有预选，不自动创建业务记录。
- 从渠道商推荐批次时，仅以真实进货关系为候选；日期接近只作为参考，不自动确定批次。多个日期不推断哪一个代表进货日期。候选扫描上限 5000，推荐最多展示 20 项，均可手动搜索补充。
- 批量识别最多两个并发；关闭窗口会取消当前请求。已完成结果持久化，重开可读取，失败可单张重试。进行中的旧请求两分钟后可重试。成功结果按图片版本、模型、提供商及提示词版本复用，重新识别需主动点击。

## 数据与接口

`SharedAttachment` 保存权威图片信息、备注、内容版本及图片版本。原有两张附件表保留记录 ID、位置和展示字段作为服务维护的投影，并新增统一附件外键；这样已有列表、附件数量及封面查询无需改为动态跨表归集。禁止在其他业务路径直接写投影；图片批量录入的原图归档路径也同步建立统一附件。

历史迁移逐条创建统一附件，保留相同文件但不同备注的历史记录。原记录 ID、图片、备注、顺序、创建时间和封面不变。普通保存改为增量维护，内容未变化时不重建关联。写操作持有附件事务锁，编辑表单提交 `attachmentsVersion`，已有附件提交 `assetId` 和 `version`；旧版本返回 `ATTACHMENT_CONFLICT`，不会覆盖其他更新。附件内容修改同步全部投影及相关所有者版本。所有位置最多 50 张附件。

- `GET /api/attachments?type=batch|distributor&q=…&page=…&ownerType=…&ownerId=…`：分页搜索目标，每页 20 项，真实采购关系优先。
- `GET /api/attachments/:id`：统一附件内容、版本和关联位置。
- `POST /api/attachments`：受控 `operation`，支持 `link`、`linkMany`、`unlink`、`update`、`merge`、`delete` 和只读冲突预检 `conflicts`。引用使用附件 ID／版本；替换图片必须使用有效上传授权，不接受外部 URL。多目标关联和集中确认的不同图片归属均在一个事务提交；冲突合并作为用户另外确认的操作提交。
- `GET /api/attachments/:id/recognition?type=…&id=…`：当前图片版本的识别状态及可用模型。
- `POST /api/attachments/:id/recognition`：`owner`、`provider`、UUID `requestId`、`force`，每次一张图片。账号来自认证会话；服务端检查附件属于指定位置。
- `DELETE /api/attachments/:id/recognition`：按当前账号和 `requestId` 取消进行中的结果写回。

复用现有图片模型配置，使用独立 `receipt-parties-v1` 提示词与严格证据结构。只提取销售方、购买方、电话、地址、日期和单据类型；不提取金额、银行账号、税号或采购行。图片整体发送到主动选择的图片模型；服务端只从受控本地／COS objectKey 读取，不接受外部图片地址。模型不接收渠道商名录，匹配在后端执行；图片文字只作为数据。

`AttachmentRecognition` 保留每次尝试的状态、图片／模型／提示词版本、证据、可取得的 token 用量和错误码。缺失用量为未知；每次失败重试独立记录，不把失败视为零成本。原始票据内容不进入普通日志或文字助手会话。使用现有认证、同源校验和数据库审计；共享内容变更通过附件投影的既有审计触发器记录。

## 迁移与验证

迁移：`20261119000000_shared_attachments`。开发库只应用本功能的精确 SQL，不自动执行其他待迁移项目，也不涉及生产部署或业务数据覆盖。

```bash
node scripts/with-dev-db.mjs tsx scripts/migrate-shared-attachments.ts --dev
node scripts/with-dev-db.mjs tsx scripts/migrate-shared-attachments.ts --dev --apply
```

脚本限制目标为专用开发库，先备份相关历史数据，再应用 SQL，比较历史记录及封面并验证统一附件投影，成功后仅标记本次迁移。报告在忽略提交的 `backups/shared-attachments/`。生产迁移应另行备份、审查和部署；不能以开发库覆盖生产。

测试入口：`shared-attachments.test.ts`、`attachment-recognition.test.ts`（隔离 `_test` 数据库）及 `attachment-receipts.test.ts`、`shared-attachment-api.test.ts`。数据库用固定模型响应验证缓存、重试、取消、晚到回调和换图失效；普通测试不发起真实模型调用。

真实图片模型检查默认不联网，显式运行：

```bash
node scripts/with-dev-db.mjs tsx scripts/check-attachment-recognition.ts --real --dev
```

该脚本发送虚构销售方／购买方和两个日期的合成票据，记录模型、证据、差异与 token 用量，不写业务库。合成票据通过不代表真实手写票据、模糊照片或所有供应商都能正确识别。

## AI 助手影响

AI 助手影响：已同步（维护说明与能力边界）；本功能是附件归档识别，文字助手仍不具备票据 OCR、附件归属查询或写入能力，识别证据不接入其事实、提示词或会话。采购、库存、金额口径与查询关系未改变，关联附件不会让文字助手误认为新增了采购关系。相关采购测试作为回归边界；不能将本功能描述为文字助手已支持票据查询。
